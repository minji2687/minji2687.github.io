> 초안. DB 설계 강의마다 "확장을 고려하라"는 말이 나와서, 실제로 뭘 조심하면 되는지 정리한 노트.

DB는 나중에 바꾸기가 제일 비싸다. 코드는 고쳐서 배포하면 끝이지만, DB는 쌓인 데이터를 옮겨야 하고 그걸 쓰는 API·화면이 같이 바뀐다.

## 1. 같은 걸 두 번 적지 않기

고객 이름을 고객 테이블과 주문 테이블에 둘 다 적어두면, 이름이 바뀔 때 한쪽만 고쳐져서 서로 달라진다.

→ 한 정보는 한 곳에만 두고, 다른 테이블에서는 **id로 연결**한다.

## 2. "이거 나중에 여러 개 되지 않을까?" 한 번 생각하기

강의에서 말하는 "확장 고려"는 대부분 이 얘기다.

### 문제: 컬럼 하나로 만들었는데 여러 개가 필요해짐

처음엔 "사용자는 역할이 하나"라서 컬럼으로 뒀다.

```sql
users
| id | name  | role  |
| 1  | minji | ADMIN |
```

나중에 "한 사람이 ADMIN이면서 OPERATOR일 수도 있다"가 되면, 이 구조로는 담을 수가 없다. `role1`, `role2`처럼 컬럼을 늘리는 건 몇 개까지 늘릴지 모르니 답이 아니다.

### 해결: 연결용 테이블(매핑 테이블)을 따로 둔다

```sql
users               roles                 user_roles  ← 누가 어떤 역할인지 한 줄에 하나씩
| id | name  |      | id | name     |      | user_id | role_id |
| 1  | minji |      | 1  | ADMIN    |      | 1       | 1       |
                    | 2  | OPERATOR |      | 1       | 2       |
```

- 역할이 하나 늘면 `user_roles`에 **줄을 하나 추가**하면 된다. 테이블 구조는 그대로.
- 역할 종류가 늘어도 `roles`에 줄만 추가하면 된다.

```sql
-- minji(id 1)의 역할 조회
SELECT r.name
FROM user_roles ur
JOIN roles r ON r.id = ur.role_id
WHERE ur.user_id = 1;
```

### 언제 처음부터 이렇게 하나

| 상황 | 선택 |
| --- | --- |
| 확실히 하나뿐 (예: 주문의 주문자) | 컬럼 하나로 충분 |
| 지금은 하나지만 늘어날 가능성이 현실적으로 있음 (역할, 태그, 담당자) | 처음부터 매핑 테이블 |
| 안 생길 것 같은 먼 미래 | 대비하지 않는다 — 복잡해지기만 함 |

### 이미 컬럼으로 만들어서 데이터가 쌓였다면

1. `roles`, `user_roles` 테이블을 새로 만든다
2. 기존 `users.role` 값을 `user_roles`로 옮긴다
3. 코드가 새 테이블을 보도록 바꾼다
4. 다 옮겨졌으면 `users.role` 컬럼을 지운다

**2번(옮기기)을 표로 보면**

옮기기 전: 역할이 `users.role` 칸에 글자로 들어 있고, `roles`에는 역할 종류가 있다.

```txt
users                           roles
| id | name  | role     |       | id | name     |
| 1  | minji | ADMIN    |       | 1  | ADMIN    |
| 2  | sora  | OPERATOR |       | 2  | OPERATOR |
| 3  | jun   | ADMIN    |
```

할 일: 사람마다 "역할 이름 → 그 이름의 roles id"를 찾아서 `user_roles`에 한 줄씩 적는다.

- minji: ADMIN → id 1 → `(1, 1)`
- sora: OPERATOR → id 2 → `(2, 2)`
- jun: ADMIN → id 1 → `(3, 1)`

옮긴 후:

```txt
user_roles
| user_id | role_id |
| 1       | 1       |
| 2       | 2       |
| 3       | 1       |
```

이걸 SQL 한 번으로 하면:

```sql
INSERT INTO user_roles (user_id, role_id)   -- user_roles에 적을 건데
SELECT u.id, r.id                           -- 사람 id, 역할 id를
FROM users u
JOIN roles r ON r.name = u.role;            -- 사람의 role 글자 = roles의 name 인 것끼리 짝지어서
```

`JOIN ... ON r.name = u.role`이 손으로 한 "역할 이름으로 id 찾기"를 사람 수만큼 자동으로 해준다.

### 옮길 때 위험한 것

데이터가 쌓인 뒤에 구조를 바꾸는 일이라, 테이블 설계에서 다들 제일 두려워하는 작업이다.

| 위험 | 무슨 일이 생기나 | 대비 |
| --- | --- | --- |
| **짝이 안 맞는 데이터** | `role`에 `admin`(소문자), `ADMN`(오타), 빈 값이 있으면 JOIN에서 짝이 안 지어져 **에러 없이 조용히 빠진다** | 옮긴 뒤 개수 비교. `users` 100명인데 `user_roles` 97줄이면 빠진 3명을 찾는다 |
| **옛 컬럼을 너무 빨리 지움** | 옮기기가 잘못됐는데 원래 값이 사라져서 되돌릴 수 없다 | 옮기기 → 코드 변경 → 한동안 확인 → **그다음에** 삭제. 지우기 전 백업 |
| **옮기는 중에 데이터가 바뀜** | 그 사이 역할 변경·신규 가입이 새 테이블에 반영 안 될 수 있다 | 사용자 적은 시간에 하거나 잠깐 쓰기를 막는다 |
| **그 컬럼을 쓰는 코드가 많음** | 화면·API·배치·다른 팀 쿼리 중 하나라도 못 고치면 컬럼 삭제 순간 깨진다 | 지우기 전에 코드 전체에서 컬럼 이름 검색 |
| **데이터가 많음** | 수백만 건이면 오래 걸리고 테이블이 잠겨 서비스가 느려지거나 멈출 수 있다 | 나눠서 옮기거나 운영 시간 외에 작업 |

{% callout type="warning" title="실무 순서" %}
**새 것 추가 → 옮기기 → 확인 → 한참 뒤에 옛 것 삭제.** 처음부터 매핑 테이블로 만들라는 것도 결국 이 과정을 피하려는 것이다.
{% /callout %}

그래서 늘어날 가능성이 보이면 처음부터 매핑 테이블로 가는 게 싸다.

## 3. 바뀔 수 있는 값을 id로 쓰지 않기

이메일이나 사번을 id(PK)로 쓰면, 그 값이 바뀌는 순간 연결된 데이터가 다 꼬인다.

→ id는 1, 2, 3… 같은 **의미 없는 번호**로 두고, 이메일처럼 겹치면 안 되는 값에는 `UNIQUE`만 건다.

{% callout type="info" title="덤" %}
`created_at`(언제 만들었는지)은 처음부터 넣어두자. 거의 항상 나중에 필요해지고, 나중에 추가하면 기존 데이터는 값이 비어 있다.
{% /callout %}
