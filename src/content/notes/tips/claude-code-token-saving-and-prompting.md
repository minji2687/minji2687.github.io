Claude Code로 작업하다 보면 세션이 길어질수록 응답이 느려지고 비용도 늘어난다는 걸 체감하게 된다. 공식 문서 기준으로 "왜 그런지"와 "어떻게 아낄 수 있는지", 그리고 "애초에 왕복을 줄이는 대화법"을 정리했다.

## 프롬프트 캐싱이 핵심 레버

대화의 앞부분(시스템 프롬프트, CLAUDE.md, 이전 대화 내용)이 안 바뀌면 그 부분은 캐시로 재사용되고, 캐시 히트는 정가 대비 **약 10% 가격**으로 처리된다. 즉 대화가 길어져도 새로 추가된 부분만 제값을 내고, 나머지는 훨씬 싸게 다시 읽히는 구조다.

**캐시를 깨는 것들 (비싼 것)**
- 모델 전환 (`/model`)
- effort 레벨 변경 (`/effort`)
- MCP 서버 연결/해제
- `/compact` 실행

**캐시를 안 깨는 것들 (괜찮은 것)**
- 파일 편집
- 스킬 호출
- `/rewind`
- 서브에이전트 스폰

그래서 실전 팁은 단순하다 — **세션 시작할 때 모델/effort를 한 번에 정하고, 작업 중간에 자주 바꾸지 않기.** 바꿀 때마다 그 시점 이후 전체가 새로 계산된다.

## 컨텍스트를 직접 들여다보는 명령어

- `/context` — 지금 뭐가 컨텍스트를 차지하고 있는지 실시간 확인
- `/compact [지시]` — 대화 히스토리를 요약해서 정리 (작업과 작업 사이 자연스러운 지점에서 하는 게 좋다)
- `/clear` — 완전히 새로 시작 (관련 없는 작업으로 넘어갈 때)
- `/cost` — 세션 토큰/비용 확인

## CLAUDE.md·메모리로 반복 설명 줄이기

"들여쓰기는 2칸, 커밋 전엔 테스트 돌려라" 같은 걸 매 세션 대화로 반복하는 대신 `CLAUDE.md`에 한 번 적어두면 세션 시작 시 자동으로 로드된다. 자동 메모리(`MEMORY.md`)도 같은 원리인데, 이건 Claude가 세션 중에 스스로 배운 걸 저장해뒀다가 다음 세션에서 재사용한다는 점이 다르다.

## 서브에이전트로 컨텍스트 격리

테스트 로그 수천 줄, 긴 문서 파싱처럼 부피 큰 작업을 서브에이전트에 위임하면 그 결과는 서브에이전트 안에만 쌓이고 메인 대화엔 요약만 돌아온다. 메인 컨텍스트가 부풀지 않는다는 뜻이다. 읽기 전용처럼 가벼운 작업엔 Haiku 같은 저렴한 모델을 지정해서 더 아낄 수도 있다.

## Plan Mode — 실행 전에 먼저 검토받기

큰 작업을 바로 실행시키는 대신, Shift+Tab으로 Plan Mode에 들어가면 접근 방식만 먼저 제안받고 검토할 수 있다. 잘못된 방향으로 갔다가 다시 갈아엎는 토큰 낭비를 실행 전에 막는 셈이다.

## 효율적으로 일 시키는 대화법

토큰 절약이 세션 관리 얘기라면, 이건 애초에 왕복 자체를 줄이는 얘기다. Anthropic 프롬프트 엔지니어링 공식 가이드 기준.

**구체적으로 말하기**
- "코드 좀 개선해줘" (X)
- "login 함수에 입력 검증 추가, 비밀번호 8자 미만이면 거부" (O)

모호한 요청은 Claude가 넓게 탐색하게 만들어서 그만큼 토큰도 더 쓴다.

**예시(few-shot) 주기**

원하는 출력 포맷·스타일 예시를 하나 주면, 왕복 질문 없이 한 번에 맞는 결과가 나올 확률이 높아진다.

**맥락을 처음에 몰아서 주기 — 한 번에 완결된 요청으로**

나쁜 패턴:
```
"함수 짜줘" → (응답) → "에러 처리도 추가해줘"
```
이러면 Claude가 방금 짠 함수를 다시 훑어서 어디에 에러 처리를 끼워 넣을지 재해석해야 한다.

좋은 패턴:
```
"이런 에러 케이스(잘못된 형식/필드 누락/타입 불일치)까지 포함한
파싱 함수 짜줘"를 처음부터 한 번에
```

**독립적인 요청은 한 번에 묶어서**

함수 A 테스트케이스, 함수 B 테스트케이스를 따로따로 시키지 말고 한 프롬프트에 같이 요청하면 왕복이 줄어든다.

**검증 기준을 같이 주기**

"principal=1000, rate=5%, 3년 → 약 1157.63"처럼 기대값을 미리 주면 Claude가 스스로 검증하고 끝낸다. "이거 틀렸어, 다시"로 왕복하는 대신.

**역할·제약을 명시**

"너는 보안 관점 코드 리뷰어야. 스타일 말고 취약점만 봐줘"처럼 역할을 좁혀주면 탐색 범위 자체가 줄어든다.

**복잡한 작업은 단계로 쪼개기**

"캐싱 레이어 설계하고 구현하고 테스트하고 최적화까지"를 한 번에 던지는 대신, 1단계(분석) → 승인 → 2단계(설계) → 승인 → 3단계(구현)로 쪼개면 잘못된 방향으로 가는 걸 초반에 잡을 수 있다.

## 정리

- 토큰 절약의 핵심은 **캐시를 안 깨는 것** — 모델/effort는 세션 시작 시 한 번만 정하고, 부피 큰 작업은 서브에이전트로 격리
- `/context`, `/compact`, `/clear`, `/cost`로 컨텍스트 상태를 직접 확인하고 관리할 수 있다
- 반복되는 규칙은 CLAUDE.md·메모리에, 반복되는 대화는 애초에 한 번에 완결된 요청으로 — 왕복 자체를 줄이는 게 캐싱보다 먼저다
- 프롬프트는 구체적으로, 예시와 검증 기준을 같이, 복잡한 작업은 단계별 승인으로 쪼개기
